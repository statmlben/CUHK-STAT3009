# STAT3009 机房 Quiz 即时提交与排行榜：实施计划

**草案日期：**2026-10-07  
**适用场景：**学生在学校机房的 JupyterLab 中完成预测题；教师希望学生一行代码得到反馈，并体验实时排行榜。  
**建议状态：**先用于一次不计分演练，通过现场验证后再用于正式考核。

## 1. 目标与边界

学生在 notebook 中生成与测试集行顺序一致的 `y_pred`，运行：

```python
submit(y_pred, student_id="1234567890")
```

系统检查请求是否来自指定机房的公网出口 IP、是否处于开放时段、学号是否在名单中、预测向量是否有效；随后在服务器端与隐藏答案比较，返回公开榜分数（例如 RMSE）和名次。教师可查看谁提交过、每次提交的时间与成绩，并导出记录。学生无需创建 Kaggle 账号、制作 CSV 或逐人领取提交码。

这个入口提供**即时反馈和现场提交限制**，不能单独证明是谁完成了代码。同一机房的学生仍可能填写别人的学号，远程控制机房电脑也不能仅靠 IP 识别。因此，正式考核继续以 Blackboard 留存的 notebook／预测文件和现场监考为依据；若最终分数使用在线评分，评分规则须在考前明确告知学生。

## 2. 学生与教师流程

| 阶段 | 学生 | 教师／系统 |
| --- | --- | --- |
| 课前 | 无需注册 | 准备训练数据、无标签测试数据、隐藏标签及名单；设定开放时间和机房出口 IP；在机房试运行 |
| Quiz 中 | 在机房 JupyterLab 运行 notebook；调用 `submit(y_pred, student_id=...)` | 服务器核对条件、计算分数、记录提交；匿名排行榜更新 |
| 截止时 | 按课程要求在 Blackboard 提交 notebook（必要时连同预测文件） | 服务器停止接收新提交，导出提交记录，核查 Blackboard 留档 |
| 截止后 | 查看教师决定公布的最终结果 | 如采用 private score，截止后才公布最终排名；处理异常与复核 |

学生端 helper 随 quiz notebook 发放，内部处理 HTTP 请求、超时与友好的错误提示。学生只接触提交 URL、公开分数和排名；隐藏标签、名单和教师管理凭据不写入 notebook 或公开 GitHub。

## 3. 建议架构

```text
机房 JupyterLab
  └─ submit(y_pred, student_id)
       └─ HTTPS POST
            └─ Cloudflare Worker：IP／时间／数据校验、评分、排行榜接口
                 └─ 私有 D1 数据库：名单、隐藏标签、提交记录

教师 ── 管理脚本／受保护的管理接口 ── 导出提交记录与成绩
学生 ── 匿名排行榜页面或 notebook 查询 ── 只看公开信息
```

选择 Worker 是因为它能在服务端读取连接来源 IP；不要采信学生在请求正文或普通自定义 header 中自报的 IP。D1 可直接绑定到 Worker，减少额外服务。GitHub 仅保存可公开的应用代码、notebook helper 和部署配置；真实 `y_test`、学号名单、管理密钥和生产数据库内容不得提交到仓库。相关能力见 [Cloudflare Worker 按 IP 响应示例](https://developers.cloudflare.com/workers/examples/conditional-response/)与 [D1 Worker binding 文档](https://developers.cloudflare.com/d1/worker-api/)。

**机房 IP 的前置确认：**从至少两三台机房电脑的 *JupyterLab kernel* 发测试请求，让服务器返回它实际看到的来源 IP。核对所有可能的 IPv4／IPv6 出口，并请 IT 确认该出口是否也供其他校园地点或校园 VPN 使用。只有当出口确实能区分机房时，IP 白名单才有“限机房”的意义。部署后必须从机房外再做一次拒绝测试。

## 4. 最小功能规格

### 提交接口 `POST /submit`

- 输入：`quiz_id`、`student_id`、按发布测试集行顺序排列的预测值。`quiz_id` 由 helper 固定传入，服务端仍须核对当前开放的 quiz。
- 校验顺序：来源 IP → 开放时段 → 学号在名单中 → 向量长度、数值类型及有限值 → 评分与记录。请求体设大小上限，防止误传大型对象。
- 成功返回：提交编号、公开分数、名次、服务器时间、剩余时间／提交状态。失败返回清楚的原因，例如“非机房网络”“quiz 尚未开放”“预测数量不对”“含 NaN”。不返回隐藏标签或逐样本误差。
- 记录：学号、时间、quiz、预测值或可复核的预测快照、分数及来源 IP；只有教师可访问。至少保留足以复核成绩的材料，保留期限遵循校方要求。
- 排行榜：每名学生默认展示其最佳**公开**成绩，别名由系统生成；学号和完整提交历史不对学生公开。并列名次、同分处理及“最佳／最后一次提交”的规则在考前写明。

### 评分与 public／private split

第一版可先用单一隐藏测试集返回 RMSE，验证完整链路。若希望模拟 Kaggle，再把隐藏测试行用固定随机种子划成 public 和 private 两部分：提交时计算并保存两项分数，只返回 public 分数；截止后再由教师决定是否公布 private 排名。这样可以展示反复追逐公开榜可能导致的过拟合。任何用于正式成绩的 private 评分比例和计算规则都应事先公布。

仅靠学号无法防止机房内代提交。因此，**第一版不要让排行榜名次自动决定个人成绩**。对于高比重考核，可结合 Blackboard 最终文件、现场核验；若之后仍需更强的在线身份确认，再评估校方登录或现场发放的一次性凭据。

## 5. 实施步骤与验收

| 阶段 | 交付物 | 验收条件 |
| --- | --- | --- |
| A. 机房网络确认 | 出口 IP 清单、网络测试记录 | 机房内请求能到达；机房外被拒绝；确认 VPN／共享出口情况 |
| B. 最小服务 | Worker、私有 D1、`/submit`、教师导出脚本 | 已知样例 RMSE 正确；错误形状、NaN、未知学号、超时段请求被拒绝 |
| C. 学生体验 | notebook helper、匿名排行榜 | 学生只需一行提交；错误信息可自行理解；不暴露学号或 private score |
| D. 演练 | 一次不计分的机房试用 | 从多台机房电脑成功提交；模拟全班集中提交；教师能导出“已交／未交” |
| E. 正式使用 | 考前配置、Blackboard 备用入口、监考说明 | 截止时间一致；服务故障时可用 Blackboard 文件恢复评分；成绩可复核 |

课前检查应包括：使用教师测试账号提交已知答案、从外网确认被拒、测试学生名单、核对服务器使用香港时间显示截止时刻、导出一次成绩表、确认 Blackboard 备用提交入口可用。若服务中断，以 Blackboard 已收到的 notebook／预测文件作为恢复依据，不让学生因在线服务故障失去提交机会。

## 6. 运维、费用与待定事项

- **预计费用：**按 2026-10 的官方文档，Workers Free 每日上限为 100,000 次请求、每次请求 10 ms CPU 时间；D1 Free 每日包含 500 万行读取、100,000 行写入，总存储 5 GB、单个数据库最多 500 MB。一般课堂规模大概率在额度内，但应以实际名单、预测向量长度和演练负载核对；达到免费额度后请求／数据库操作可能失败。[Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) · [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
- **数据管理：**使用仅教师可访问的 Cloudflare 账户和数据库；生产数据不进入公开仓库。正式使用前确认学校是否允许把学号、提交记录和成绩放在该外部服务；如不允许，保留相同接口设计，改部署在学校批准的服务器。
- **需要教师最终确定：**本系统用于哪一次 quiz；公开榜分数是否参与正式成绩、占比多少；每人是否限制提交次数；成绩按最佳、最后一次或 private score 计算；榜单是否只在机房／考试期间可见。这些都是考核规则，须在学生开始前固定并公布。

**建议的第一步：**先用一份小型模拟测试集做不计分原型，并完成机房内外的 IP 验证。网络边界确认后再导入真实试题与名单。
